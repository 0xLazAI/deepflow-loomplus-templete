# Questions for Main Coordinator

## Purpose
本文件是提问策略参考库，不是固定问卷。
你不需要每次逐条提问。
你应根据当前项目类型、当前阶段、当前缺失信息和当前阻塞点，选择最少必要问题进行追问。

## Questioning principles
- 先问会阻塞流程推进的问题
- 先问会影响 FE / BE scope 的问题
- 先问会影响字段、权限、商业规则的问题
- 能通过默认假设先推进的，不优先追问
- 能从已有文档判断的，不重复问
- 一次只问最少必要问题，不连续抛大量开放问题
- 优先用短问题、选择题、确认题
- 不把 FE / BE 的技术术语原样丢给需求方，应翻译成需求方能判断的话
- 同一轮最多优先抛出 1 到 3 个阻塞性问题；超过 3 个时，先收敛为最关键的 1 到 3 个

## How to use this file
- 本文件提供的是“问题类型 + 可用表达方式”
- 你可以根据当前项目类型即时拟定问题
- 你不需要机械地照抄下面所有问题
- 不影响最小 MVP 推进的问题，优先记入 `01_product/open_questions.md`
- 未落盘的默认假设，不得作为正式执行依据

## Question categories

### A. Goal clarification
用于确认这轮到底要验证什么。

可用问题：
- 这轮最想先解决什么问题？
- 这轮最想先验证什么？
- 这轮更偏演示验证，还是偏正式交付？
- 这轮你更希望先看到哪一种结果？
  - PRD
  - 页面结果
  - 后端方案
  - 可跑的 MVP

### B. Scope clarification
用于确认第一版必须做什么、暂时不做什么。

可用问题：
- 第一版必须包含哪些功能？
- 哪些功能可以延后？
- 这轮是否涉及以下内容：
  - 登录 / 注册
  - 权限控制
  - 导出
  - 通知
  - 支付
  - 第三方 API

### C. User and scenario clarification
用于确认目标用户和核心场景。

可用问题：
- 主要用户是谁？
- 主要使用场景是什么？
- 有没有参考产品、参考页面或参考流程？
- 这轮最关键的用户路径是什么？

### D. Data and field clarification
用于确认字段和结构，避免 FE / BE 收到模糊 handoff。

可用问题：
- 需要收集哪些关键字段？
- 哪些字段是必填，哪些可以先简化？
- 数据是否需要查询、编辑、删除、导出？
- 有没有必须保留的业务字段或状态字段？

### E. Rule clarification
用于确认关键业务规则。

可用问题：
- 有没有必须遵守的业务规则？
- 有没有权限差异？
- 有没有审核、审批、发布、确认等流程？
- 有没有不能默认处理的商业规则？

### F. Delivery clarification
用于确认这轮什么算“能继续”。

可用问题：
- 你判断这轮结果“可以继续”的标准是什么？
- 当前这轮，你更希望先快出结果，还是先把规则定义完整？
- 当前这轮，最重要的 review 点是什么？

## Mandatory clarification triggers
只有出现以下情况，才必须立即追问，不要自行补全：
- 影响主用户路径
- 影响 FE / BE 边界
- 影响字段定义
- 影响权限或商业规则
- 影响 handoff 是否能成立
- 影响 receipt 是否能被正确汇总

## Non-blocking questions
以下问题如果不影响最小 MVP，可以先不追问，先记入 `01_product/open_questions.md`：
- 低优先级优化项
- 非核心交互偏好
- 不影响主流程的扩展功能
- 不影响本轮推进的次要字段
- 可通过默认假设先处理的细节

## Default assumption rule
如果某个问题暂时不追问，但仍与执行相关，则必须把默认假设写入：
- `01_product/open_questions.md`
或
- 对应的 handoff 文档

默认假设边界：
- 可以默认：
  - 不影响主流程的低优先级展示细节
  - 不影响字段结构的非核心交互偏好
  - 当前轮明确暂不做的扩展能力
- 不可以默认：
  - 主用户路径是否成立
  - FE / BE 边界
  - 必填字段与关键状态字段
  - 权限、审核、审批、计费、商业规则
- 若某问题既可能影响主流程，又暂时无法确认，则不得用默认假设硬推进，必须转入 clarification_pending 或 blocked

## Escalation rule
若当前问题会阻塞 handoff 或使项目进入 `blocked`，则必须：
1. 在 `01_product/open_questions.md` 中记录
2. 在 `00_meta/project_status.md` 中体现
3. 向需求方明确说明：
   - 当前卡点是什么
   - 为什么会阻塞
   - 需要确认什么
   - 下一步是什么
